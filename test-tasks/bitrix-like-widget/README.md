# Тестовое задание: AJAX-виджет «Лайк» для 1С-Битрикс

Реализация выполнена для 1С-Битрикс без прямых SQL-запросов.

## Файлы

- `like-handler.php` - backend-обработчик: валидация входных данных, CSRF-проверка, защита от повторного лайка через PHP-сессию, чтение и обновление свойства инфоблока штатным API.
- `like.js` - асинхронный `fetch`, блокировка повторного запроса во время выполнения, обработка HTTP/JSON ошибок, обновление счетчика и состояния кнопки без перезагрузки страницы.
- `markup.html` - пример разметки и минимальных стилей.

## Предположения

- Используется инфоблок с ID `7`.
- Числовое свойство с кодом `LIKES` хранит текущее количество лайков.
- `prolog_before.php` доступен и сессия Битрикса инициализирована.
- На странице доступен глобальный объект `BX`, поэтому frontend отправляет `BX.bitrix_sessid()` для CSRF-проверки.
- Путь обработчика в примере - `/ajax/like-handler.php`, путь JS - `/local/js/like.js`. В реальном проекте они корректируются под структуру сайта.

## Безопасность и поведение

`id` проходит `FILTER_VALIDATE_INT` с минимальным значением 1. `action` допускает только `like` и `unlike`. Элемент дополнительно ищется только в ожидаемом инфоблоке.

Для гостя состояние лайка хранится в `$_SESSION`. Операции сделаны идемпотентными в рамках сессии: повторный `like` не увеличивает счетчик второй раз, а `unlike` без активного лайка не уменьшает его.

Запросы принимаются только методом POST. Используется `check_bitrix_sessid()`.

На frontend кнопка блокируется на время запроса, чтобы двойной клик не создавал параллельные операции. Ошибки сети, HTTP и некорректный JSON обрабатываются без изменения текущего UI-состояния.

## Ограничение решения

По условиям тестового счетчик хранится в свойстве инфоблока и обновляется через `CIBlockElement::SetPropertyValuesEx`. Это простой read-modify-write сценарий. При большой конкурентной нагрузке два одновременных запроса теоретически могут прочитать одно старое значение. Для production-системы с высокой частотой лайков я бы вынес события лайков в отдельную сущность Highload-блока с уникальностью по пользователю/гостевому идентификатору и элементу, а агрегированный счетчик формировал бы отдельно. Для данного тестового это было бы избыточно.

## Проверка

Локально выполнены синтаксические проверки файлов без разворачивания CMS, как и требуется в задании:

```bash
php -l like-handler.php
node --check like.js
```

PHP-файл проходит `php -l`, JavaScript проходит `node --check`.
